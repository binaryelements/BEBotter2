# Admin UI on the BE Design System Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The admin site ("BE Team Botter") looks and reads like BE Hub: the Binary Elements design system, a side menu, an Overview screen, a tabbed bot page, and a timing bar in Activity.

**Architecture:** Keep server-rendered pages (Express + the `html` template helper). Vendor the design system's `tokens.css`, `components.css` and logos into `src/admin/assets/be/`, served under `/admin/assets/`, with a sync script that records the design system commit. One `layout()` gives every page the shell (brand header, grouped side menu by role, theme). Screens switch to `be-*` classes.

**Tech Stack:** Node 24, TypeScript, Express, the existing `html` helper, vitest. Design system: github.com/binaryelements/be-design-system (main @ 9f1357b), plus the four components Task 1 adds.

**Spec:** Martin, 2026-10-31: "I need a UI properly created for the admin site. Called BE Team Botter", "look at design system", "if design system can be made better, make it", "Can we fix the ui based on the design system repo". Proposal canvas: https://claude.ai/artifact/QmUiCw8eCtWji7vzqvq8QX (Overview, Bot page with tabs, Activity). Design system README (voice, visual foundations) is binding.

## Global Constraints

- No new npm dependencies; no client-side framework. Pages work without JavaScript; a few lines of inline script only for the theme toggle.
- Design system rules: lowercase labels on buttons, fields and tabs; verb-first actions; no confirm pop-ups (a destructive action arms on first press and acts on the second); one primary button per view; status never colour alone; IBM Plex from Google Fonts; dark and light both work (follow the device unless the person picks one; the choice is a cookie).
- Every value comes from the design system's tokens; no hex colours in the app's CSS.
- Behaviour, routes, forms, CSRF and access rules stay exactly as they are; only markup and copy change, plus the new Overview screen and the bot page tabs (which reorganise existing sections, no new actions).
- Pages work at phone width (menu stacks, tables scroll in a box).
- No secrets or keys ever rendered (existing tests keep asserting this).
- Top-level `import type` only; tests offline.

## Review Focus

1. A head (not admin) signs in: the menu shows only what heads may open, and every hidden screen still answers 403 directly.
2. Dark and light: every screen reads in both (contrast comes from the tokens; no screen sets its own colours).
3. A long table (People with many rows, Activity) on a phone: it scrolls in its box, the page does not scroll sideways.
4. Theme cookie missing, invalid or set: the page renders, defaulting to the device.
5. Every form still posts its CSRF token and every destructive action still needs its second press (or the existing confirmation step).

- `be-seg`: a radio group shown as joined segments (label wrapping a visually hidden radio; checked segment uses `sel-bg`/`cyan`; focus ring 2px `cyan`).

- `be-pagehead`: breadcrumb line (mono, muted) + title (sans 600) + meta line (mono, muted, ` · ` separated) + actions on the right, wrapping.
